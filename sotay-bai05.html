Bai05 · SQLite và DBHelper

Sổ tay bài 5 — dữ liệu xuống CSDL

Giao diện giữ y hệt bài 4. Toàn bộ điểm mới nằm ở chỗ dữ liệu người dùng không còn nằm trong ArrayList của RAM nữa mà nằm trong một file SQLite trên máy, truy cập qua hai lớp mới: DBHelper (tạo file và bảng) và UserDAO (sáu hàm đọc/ghi). Đọc xong trang này là biết dữ liệu đi đường nào, sửa ở đâu, và trả lời được vấn đáp.

02Ba lớp SQLite phải thuộc

Android dựng sẵn SQLite trong hệ điều hành, không phải cài thư viện. Chỉ cần nhớ ba lớp và một lớp phụ.

LớpViệc của nóTrong bài này
SQLiteOpenHelperTạo file db, tạo bảng lần đầu, nâng cấp khi đổi phiên bảnDBHelper kế thừa nó
SQLiteDatabaseCái "tay cầm" để chạy SQL: insert, update, delete, rawQuery, execSQLdbHelper.writableDatabase / .readableDatabase
CursorCon trỏ chạy trên kết quả SELECT, đọc từng dòngLặp bằng moveToNext(), đọc bằng getString()
ContentValuesCái túi cột → giá trị để đưa cho insert/updateHàm valuesOf(u)

writableDatabase và readableDatabase khác gì nhau

Thực tế cả hai trả về cùng một đối tượng ghi được. Gọi readableDatabase chỉ để nói rõ ý định "chỗ này chỉ đọc thôi". Lần gọi đầu tiên của cả hai sẽ mở file db, và nếu file chưa có thì chính lúc đó onCreate() mới chạy.

Vì sao phải dùng dấu ? chứ không nối chuỗi

SAInối chuỗi
// Nếu username chứa dấu ' là câu SQL vỡ,
// tệ hơn là bị SQL injection
rawQuery("SELECT * FROM user " +
  "WHERE username = '" + un + "'", null)
ĐÚNGtham số hóa
// Giá trị đi riêng, SQLite tự bọc an toàn
rawQuery("SELECT * FROM user " +
  "WHERE username = ?",
  arrayOf(un))

03DBHelper — tạo file và bảng

Nhiệm vụ duy nhất: trả lời câu hỏi "file CSDL tên gì, trong đó có bảng gì". Không có câu lệnh đọc/ghi dữ liệu nào ở đây — tất cả nằm bên UserDAO.

DBHelper.ktkhai báo
class DBHelper(context: Context) :
    SQLiteOpenHelper(context, DB_NAME, null, DB_VERSION) {

    companion object {
        private const val DB_NAME = "quanlind.db"
        private const val DB_VERSION = 1

        const val TABLE = "user"
        const val COL_ID = "id"
        const val COL_USERNAME = "username"
        const val COL_PASSWORD = "password"
        const val COL_FULLNAME = "fullname"
        const val COL_DOB = "dob"
    }

onCreate — chỉ chạy đúng một lần

Chạy vào lần đầu mở CSDL mà file chưa tồn tại. Đã có file rồi thì không bao giờ chạy lại, kể cả khi ta sửa code trong đó. Đây là cái bẫy hay dính nhất, xem mục Sự cố thực tế.

DBHelper.ktonCreate
override fun onCreate(db: SQLiteDatabase) {
    // username là UNIQUE: nhờ vậy insert một username đã có sẽ tự hỏng và
    // UserDAO.add() trả về false, không cần tự đi dò danh sách nữa.
    db.execSQL(
        "CREATE TABLE $TABLE (" +
            "$COL_ID INTEGER PRIMARY KEY AUTOINCREMENT, " +
            "$COL_USERNAME TEXT NOT NULL UNIQUE, " +
            "$COL_PASSWORD TEXT NOT NULL, " +
            "$COL_FULLNAME TEXT NOT NULL, " +
            "$COL_DOB TEXT NOT NULL)"
    )

    insertSeed(db, "B23DCAT280", "20082005", "Trần Xuân Thành", "20/08/2005")
    insertSeed(db, "nd1", "12345678", "Nguyễn B", "12/03/2005")
    insertSeed(db, "nd2", "12345678", "Trần C", "02/11/2004")
    insertSeed(db, "nd3", "12345678", "Lê Thị D", "25/07/2005")
    insertSeed(db, "nd4", "12345678", "Hoàng E", "08/01/2003")
}

onUpgrade — xóa sạch làm lại

DBHelper.ktonUpgrade
override fun onUpgrade(db: SQLiteDatabase, oldVersion: Int, newVersion: Int) {
    db.execSQL("DROP TABLE IF EXISTS $TABLE")
    onCreate(db)
}
Biết mà trả lời: cách này mất sạch dữ liệu người dùng. Chấp nhận được với bài tập. App thật phải dùng ALTER TABLE để giữ lại dữ liệu cũ.

04UserDAO — đúng 6 hàm như UML

DAO viết tắt của Data Access Object: lớp trung gian duy nhất được phép viết SQL. Các Activity chỉ gọi hàm và nhận về User, không bao giờ nhìn thấy câu SQL nào. Đổi CSDL sang thứ khác thì chỉ sửa lớp này.

HàmTrả vềAi gọiSQL bên dưới
add(u)BooleanAddActINSERT
edit(u)BooleanEditActUPDATE … WHERE id = ?
delete(id)BooleanUserhomeActDELETE … WHERE id = ?
search(key)ArrayList<User>LoginActSELECT … LIKE ?
getAll()ArrayList<User>UserhomeActSELECT *
checkLogin(u)BooleanLoginActSELECT id … WHERE un = ? AND pw = ?

add — dựa vào UNIQUE để chặn trùng

UserDAO.ktadd
fun add(u: User): Boolean {
    val db = dbHelper.writableDatabase
    // insert trả về -1 khi vi phạm ràng buộc UNIQUE
    val id = db.insert(DBHelper.TABLE, null, valuesOf(u))
    return id != -1L
}

insert() trả về id của dòng mới, hoặc -1 nếu hỏng. Nó không ném ngoại lệ khi trùng UNIQUE — đây là lý do chọn nó thay vì execSQL.

edit — vì sao phải CONFLICT_IGNORE

UserDAO.ktedit
fun edit(u: User): Boolean {
    val db = dbHelper.writableDatabase
    val rows = db.updateWithOnConflict(
        DBHelper.TABLE,
        valuesOf(u),
        "${DBHelper.COL_ID} = ?",
        arrayOf(u.id.toString()),
        SQLiteDatabase.CONFLICT_IGNORE
    )
    return rows > 0
}
Khác với insert: db.update() thường sẽ ném SQLiteConstraintException khi username mới trùng người khác, làm app văng. updateWithOnConflict(… CONFLICT_IGNORE) thì bỏ qua lặng lẽ và trả về 0 dòng, để mình hiện Toast báo trùng cho đẹp.

query — chỗ duy nhất đọc Cursor

Cả getAll() lẫn search() đều gọi chung hàm riêng này, nên code đọc Cursor chỉ viết một lần.

UserDAO.ktquery + userOf
private fun query(sql: String, args: Array<String>?): ArrayList<User> {
    val db = dbHelper.readableDatabase
    val cursor = db.rawQuery(sql, args)
    val list = ArrayList<User>()
    while (cursor.moveToNext()) {     // nhảy sang dòng kế, hết thì false
        list.add(userOf(cursor))
    }
    cursor.close()                     // KHÔNG quên, nếu không sẽ rò bộ nhớ
    return list
}

private fun userOf(c: Cursor) = User(
    id       = c.getInt(c.getColumnIndexOrThrow(DBHelper.COL_ID)),
    username = c.getString(c.getColumnIndexOrThrow(DBHelper.COL_USERNAME)),
    password = c.getString(c.getColumnIndexOrThrow(DBHelper.COL_PASSWORD)),
    fullname = c.getString(c.getColumnIndexOrThrow(DBHelper.COL_FULLNAME)),
    dob      = toDate(c.getString(c.getColumnIndexOrThrow(DBHelper.COL_DOB)))
)
Lệnh CursorLàm gì
moveToNext()Nhảy sang dòng tiếp theo, trả false khi hết — hợp với vòng while
moveToFirst()Nhảy về dòng đầu, trả false nếu rỗng — dùng cho checkLogin
getColumnIndexOrThrow("x")Tên cột → số thứ tự cột; sai tên thì ném lỗi ngay chứ không âm thầm
getString(i), getInt(i)Đọc ô tại cột thứ i của dòng hiện tại
close()Trả bộ nhớ. Bắt buộc, kể cả khi kết quả rỗng

checkLogin — chỉ hỏi "có hay không"

UserDAO.ktcheckLogin
fun checkLogin(u: User): Boolean {
    val db = dbHelper.readableDatabase
    val cursor = db.rawQuery(
        "SELECT ${DBHelper.COL_ID} FROM ${DBHelper.TABLE} " +
            "WHERE ${DBHelper.COL_USERNAME} = ? AND ${DBHelper.COL_PASSWORD} = ?",
        arrayOf(u.username, u.password)
    )
    val found = cursor.moveToFirst()
    cursor.close()
    return found
}

Chỉ SELECT id chứ không SELECT *: chỉ cần biết có dòng nào khớp hay không, kéo thêm cột là phí. Cũng vì thế mà nó không trả về họ tên — xem mục sau.

Màn Home — onResume là chỗ làm tươi duy nhất

Android gọi onResume() mỗi lần màn hình quay lại tiền cảnh, kể cả ngay sau onCreate(). Nên chỉ cần đặt reload() ở đó là cả ba trường hợp đều đúng: mở lần đầu, quay về từ màn Thêm, quay về từ màn Sửa.

UserhomeAct.ktreload + onResume
/** Đọc lại toàn bộ người dùng từ CSDL và vẽ lại ListView. */
private fun reload() {
    listUser.clear()
    listUser.addAll(dao.getAll())
    adapter.notifyDataSetChanged()
}

override fun onResume() {
    super.onResume()
    reload()
}
Bấm Hủy thì sao? Vẫn chạy onResume() và vẫn đọc lại CSDL, nhưng vì màn Hủy không ghi gì nên dữ liệu đọc về y hệt, nhìn ra ngoài là "không đổi". Đúng yêu cầu slide 9 và 10.

06Ngày sinh: Date trong code, TEXT trong CSDL

SQLite không có kiểu ngày tháng. Chỉ có NULL, INTEGER, REAL, TEXT, BLOB. Nên ngày sinh phải quy ước cất thành một trong ba dạng:

CáchƯuNhược
TEXT "dd/MM/yyyy" ← bài này dùngMở file db ra đọc hiểu ngay, đúng định dạng hiện trên giao diệnSắp xếp theo ngày bị sai thứ tự
TEXT "yyyy-MM-dd"Sắp xếp chữ cũng đúng thứ tự thời gianPhải đổi định dạng khi hiển thị
INTEGER (mili giây)Gọn, so sánh nhanhNhìn vào file db không đọc được
UserDAO.ktcompanion object
companion object {
    private fun format() = SimpleDateFormat("dd/MM/yyyy", Locale.getDefault())

    fun toText(date: Date): String = format().format(date)

    fun toDate(text: String): Date = try {
        format().parse(text) ?: Date()
    } catch (e: java.text.ParseException) {
        Date()
    }
}
Ba câu hỏi hay bị vặn:
  • Sao format() là hàm chứ không phải hằng số? SimpleDateFormat không an toàn khi nhiều luồng dùng chung. Tạo mới mỗi lần là chắc chắn đúng.
  • Sao phải try/catch? Dữ liệu trong CSDL có thể hỏng hoặc sai định dạng; bắt lỗi rồi trả ngày hôm nay thì app không văng.
  • Sao để trong companion object? Để AddAct và EditAct gọi thẳng UserDAO.toDate(...) mà không cần tạo đối tượng DAO.

01User có thêm thuộc tính id›

UML vẽ User chỉ có username, password, fullname, dob.

Nhưng cũng chính UML đó ghi delete(id : int) : boolean và edit(u : User) : boolean. Muốn xóa hay sửa đúng một dòng thì phải có khóa chính. Nếu không thêm id thì chỉ còn cách lấy username làm khóa, mà như thế thì không sửa được username nữa. Nên thêm id là bắt buộc về mặt kỹ thuật.

03ShowUserFrag / MenuItemFrag không phải Fragment›

Tên có chữ "Frag" nhưng là custom View, kế thừa ConstraintLayout và LinearLayout.

  • ShowUserFrag là một dòng của ListView. Android không cho mỗi dòng danh sách là một Fragment.
  • MenuItemFrag nếu làm DialogFragment thì hộp menu nhảy ra giữa màn hình, mất kiểu neo ngay dưới dấu ••• như wireframe slide 5.
  • Cả hai vẫn có hàm onCreate() đúng tên UML vẽ; chỉ khác là do khối init gọi chứ không phải hệ thống gọi.

11Sự cố thực tế đã gặp

1. Sửa dữ liệu mẫu mà chạy lên không thấy đổi

Vì onCreate() của SQLiteOpenHelper chỉ chạy khi file db chưa tồn tại. Cài đè lên bản cũ thì file vẫn còn nên nó không chạy. Gỡ app hoặc tăng DB_VERSION.

2. Sửa username thành trùng người khác thì app văng

db.update() ném SQLiteConstraintException khi vi phạm UNIQUE. Đã đổi sang updateWithOnConflict(… CONFLICT_IGNORE) để nó trả về 0 dòng, rồi edit() trả false và màn hình hiện Toast.

3. Dùng onActivityResult thì lệch UML

Bản đầu dùng onActivityResult + startActivityForResult. UML slide 7 không có hàm đó, chỉ có onResume(). Đã đổi sang startActivity() + onResume(), bỏ luôn setResult() ở hai màn con.

4. Menu ••• ở dòng cuối bị cụt mất nút Xóa

PopupWindow.showAsDropDown() luôn xổ xuống dưới, không tự lật lên khi hết chỗ. Ở màn hình ngang, dòng cuối sát đáy nên nút Xóa nằm ngoài màn hình. Lỗi có sẵn từ bài 4, không phải do bài 5. Muốn sửa thì tự tính chỗ trống rồi gọi showAsDropDown(anchor, 0, -height).

5. Cursor quên đóng

Không đóng thì logcat cảnh báo Finalizing a Cursor that has not been deactivated or closed và rò bộ nhớ dần. Trong bài này mọi rawQuery đều có cursor.close() đi kèm.

12Bộ câu hỏi & trả lời

A · SQLite và DBHelper

QSQLiteOpenHelper để làm gì, sao không tự mở file db?›

Nó lo hộ ba việc khó: tạo file đúng thư mục riêng của app, gọi onCreate() đúng một lần khi file chưa có, và gọi onUpgrade() khi số phiên bản tăng. Tự làm thì phải tự kiểm tra file tồn tại, tự quản lý phiên bản, dễ sai.

QonCreate của DBHelper chạy lúc nào?›

Lúc gọi writableDatabase hoặc readableDatabase lần đầu tiên mà file db chưa tồn tại. Không phải lúc new DBHelper(...) — constructor không mở file.

QonUpgrade chạy khi nào? Code trong đó có vấn đề gì?›

Khi DB_VERSION trong code lớn hơn số phiên bản ghi trong file db. Code hiện tại DROP TABLE rồi tạo lại nên mất sạch dữ liệu — chấp nhận với bài tập, app thật phải dùng ALTER TABLE ADD COLUMN.

QwritableDatabase với readableDatabase khác gì?›

Trên thực tế trả về cùng một đối tượng ghi được. Khác nhau về mặt diễn đạt ý định. Chỉ khi đĩa đầy hoặc file chỉ-đọc thì readableDatabase mới trả về bản chỉ đọc thật.

B · UserDAO

QVì sao phải tách UserDAO ra, viết thẳng SQL trong Activity không được à?›

Được nhưng tệ. Tách ra thì: SQL chỉ nằm một chỗ dễ sửa, Activity không phụ thuộc vào việc dữ liệu lưu ở đâu, muốn đổi sang Room hay server chỉ cần viết lại DAO, và muốn viết test cũng dễ hơn.

Qadd() biết username trùng bằng cách nào?›

Không tự kiểm tra. Cột username khai báo UNIQUE nên SQLite từ chối, db.insert() trả về -1, hàm trả false. Để CSDL lo là chắc hơn tự dò, vì tự dò có thể bị hai luồng chen nhau.

QSao edit() dùng updateWithOnConflict chứ không dùng update?›

update() ném SQLiteConstraintException khi username mới trùng, app văng. updateWithOnConflict với CONFLICT_IGNORE bỏ qua lặng lẽ, trả 0 dòng, mình bắt được để hiện Toast.

Qsearch() có nhược điểm gì?›

Dùng LIKE '%key%' nên khớp cả chuỗi con: tìm nd1 ra luôn nd10. Vì thế LoginAct phải lọc lại bằng firstOrNull { it.username == ... }. Ngoài ra % đứng đầu làm SQLite không dùng được chỉ mục, danh sách lớn sẽ chậm.

QcheckLogin trả Boolean thì lấy fullname ở đâu ra?›

Hỏi CSDL lần thứ hai bằng search(username). Đây là hệ quả của việc UML quy định checkLogin chỉ trả Boolean. Nếu được thiết kế lại, cho nó trả về User? sẽ gọn hơn, chỉ cần một lần truy vấn.

C · Cursor và ContentValues

QCursor là gì?›

Con trỏ trỏ vào kết quả của câu SELECT, ban đầu đứng trước dòng đầu tiên. moveToNext() đẩy nó xuống một dòng và trả false khi hết — nên vòng while (cursor.moveToNext()) duyệt đúng mọi dòng.

QKhông gọi cursor.close() thì sao?›

Rò bộ nhớ và rò con trỏ file. Logcat sẽ cảnh báo Finalizing a Cursor that has not been deactivated or closed. Nhiều quá thì app chậm rồi lỗi.

QSao dùng getColumnIndexOrThrow chứ không getColumnIndex?›

getColumnIndex trả về -1 khi sai tên cột, rồi getString(-1) mới nổ ở chỗ khác, khó tìm. OrThrow nổ ngay tại chỗ với tên cột sai in ra rõ ràng.

QContentValues khác gì so với viết thẳng câu INSERT?›

Là cái map tên cột → giá trị. Dùng nó thì Android tự sinh câu SQL và tự bọc giá trị an toàn, khỏi lo dấu nháy hay SQL injection. Viết tay execSQL phải tự lo hết.

QSao valuesOf() không đưa id vào?›

Vì id là AUTOINCREMENT, SQLite tự đánh khi INSERT. Còn khi UPDATE thì id đã nằm ở mệnh đề WHERE rồi, không cần ghi đè.

D · Luồng và vòng đời

QVì sao làm tươi danh sách ở onResume mà không phải onCreate?›

onCreate() chỉ chạy một lần lúc dựng màn hình. Quay về từ màn Thêm/Sửa thì Activity vẫn sống, chỉ onResume() chạy lại. Đặt ở onResume() bao trùm cả lần đầu vì onResume() luôn chạy ngay sau onCreate().

QBấm Hủy thì danh sách có bị đọc lại không?›

Có, vì onResume() luôn chạy. Nhưng màn Hủy không ghi gì vào CSDL nên dữ liệu đọc về y hệt, người dùng không thấy khác biệt — vẫn đúng tinh thần "không cần cập nhật" của slide.

QVì sao AddAct tự gọi dao.add() chứ không trả User về cho Home?›

Slide 9 ghi rõ: hàm xử lý nút Thêm đóng gói dữ liệu thành User rồi gọi hàm add() của lớp UserDAO. Làm đúng vậy thì Home chỉ còn một việc là đọc lại, code gọn hơn bài 4.

QUser vẫn truyền qua Intent, vậy Serializable còn cần không?›

Còn. LoginAct truyền User đang đăng nhập sang UserhomeAct, và UserhomeAct truyền User cần sửa sang EditAct. Hai chỗ đó vẫn đi qua putExtra nên lớp User phải Serializable.

QVì sao UserDAO nhận applicationContext?›

DAO giữ DBHelper, mà DBHelper giữ Context. Nếu giữ thẳng Activity thì Activity bị đóng rồi vẫn không được thu hồi — rò bộ nhớ. applicationContext sống cùng app nên an toàn.

E · Câu hỏi mở

QMật khẩu lưu thô như vậy có vấn đề gì? Sửa thế nào?›

Ai mở được file db là đọc được hết mật khẩu. Đúng ra phải băm bằng thuật toán chậm có muối (bcrypt, scrypt, Argon2), CSDL chỉ lưu chuỗi băm; lúc đăng nhập thì băm cái người dùng gõ rồi so hai chuỗi băm. Bài tập để thô cho dễ nhìn.

QTruy vấn CSDL trên luồng chính có sao không?›

Với vài chục dòng thì không thấy gì. Dữ liệu lớn sẽ làm giao diện khựng, quá 5 giây là hệ thống báo ANR. App thật phải đẩy xuống luồng nền (coroutine, AsyncTask cũ, hoặc Room trả về Flow).

QNếu dùng Room thay vì tự viết DAO thì khác gì?›

Room là lớp bọc trên SQLite do Google làm: mình khai báo @Entity, @Dao với câu SQL trong annotation, Room tự sinh code đọc Cursor. Lợi là được kiểm tra câu SQL ngay lúc biên dịch và không phải tự viết userOf(). Bài này tự viết tay để hiểu phần bên dưới.

QVì sao không dùng username làm khóa chính luôn?›

Vì màn Sửa cho phép đổi username. Nếu username là khóa chính thì đổi nó đồng nghĩa với xóa dòng cũ và thêm dòng mới. Dùng id tự tăng thì username đổi thoải mái mà vẫn là cùng một người.
