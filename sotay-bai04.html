Bai04 · Menu và Spinner

Sổ tay bài 4 — đọc, sửa, và bảo vệ

Ứng dụng Android viết bằng Kotlin với View system cổ điển (không Jetpack Compose, không AppCompat). Bài 4 giữ nguyên bài toán quản lý người dùng của bài 3 nhưng thay màn "Xem người dùng" bằng menu xổ ra ngay trên từng dòng, và thêm trường ngày sinh chọn bằng lịch. Trang này viết để đọc xong là biết mọi thành phần giao diện nằm ở đâu, sinh ra thế nào, sửa ở đâu, và trả lời được câu hỏi vấn đáp.

Cách hai màn con trả dữ liệu về

Dùng bộ ba cổ điển: startActivityForResult → setResult → onActivityResult. Con số requestCode chính là thứ giúp màn Home biết kết quả vừa nhận là của Thêm hay của Sửa.

KotlinUserhomeAct.kt
companion object {
    private const val REQ_ADD = 1
    private const val REQ_EDIT = 2
}

// đi
startActivityForResult(Intent(this, AddAct::class.java), REQ_ADD)

// về
override fun onActivityResult(requestCode: Int, resultCode: Int, data: Intent?) {
    if (resultCode != Activity.RESULT_OK || data == null) return
    val returned = data.getSerializableExtra("user", User::class.java) ?: return
    when (requestCode) {
        REQ_ADD  -> { /* chặn trùng rồi listUser.add(returned) */ }
        REQ_EDIT -> { /* chặn trùng rồi listUser[editingPosition] = returned */ }
    }
    adapter.notifyDataSetChanged()
}
Vì sao editingPosition tồn tại: EditAct chỉ trả về đối tượng User, không trả về vị trí. Không thể dò lại theo username vì người dùng có quyền đổi chính username đó. Nên Home ghi nhớ vị trí ngay lúc mở màn sửa.

Dữ liệu đi qua Intent bằng cách nào

User hiện thực Serializable nên đặt thẳng vào Intent bằng putExtra("user", user). Lấy ra phải tách hai nhánh vì bản API 33 trở lên đổi chữ ký hàm:

Kotlinđọc extra an toàn
val received = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
    intent.getSerializableExtra("user", User::class.java)   // API 33+, có kiểm kiểu
} else {
    intent.getSerializableExtra("user") as? User          // bản cũ, đã deprecated
}

05Hai custom View: ShowUserFrag và MenuItemFrag

Đây là phần "mới" nhất của bài 4. Cả hai đều là lớp con của View (không phải Fragment thật, dù slide đặt tên là …Frag), tự thổi layout của mình vào trong constructor.

ShowUserFrag — một dòng của danh sách

KotlinShowUserFrag.kt
class ShowUserFrag @JvmOverloads constructor(
    context: Context, attrs: AttributeSet? = null, defStyleAttr: Int = 0
) : ConstraintLayout(context, attrs, defStyleAttr) {

    private val txtUser: TextView
    private val lblMenu: TextView

    init {
        LayoutInflater.from(context).inflate(R.layout.showuser, this, true)
        txtUser = findViewById(R.id.lblUser)
        lblMenu = findViewById(R.id.lblMenu)
    }

    fun bind(user: User) { txtUser.text = user.username + "\n" + user.fullname }

    fun setOnMenuClickListener(action: (View) -> Unit) {
        lblMenu.setOnClickListener { action(lblMenu) }
    }
}
  • inflate(layout, this, true) — tham số thứ ba true nghĩa là gắn luôn con vào chính nó, nên không cần addView.
  • showuser.xml mở đầu bằng <merge> + tools:parentTag: merge để tránh sinh thêm một ViewGroup lồng vô ích (lớp này đã là ConstraintLayout rồi), còn tools:parentTag chỉ để Android Studio biết mà vẽ preview, không ảnh hưởng lúc chạy.
  • @JvmOverloads sinh đủ 3 constructor mà hệ thống inflate cần khi View được đặt trong XML.
  • setOnMenuClickListener truyền lại chính lblMenu ra ngoài — vì bên ngoài cần đúng View đó làm mốc neo popup.

MenuItemFrag — menu xổ ra

KotlinMenuItemFrag.kt
fun showAt(anchor: View, onEdit: () -> Unit, onDelete: () -> Unit) {
    this.onEdit = onEdit
    this.onDelete = onDelete
    popup = PopupWindow(this,
        ViewGroup.LayoutParams.WRAP_CONTENT,
        ViewGroup.LayoutParams.WRAP_CONTENT,
        true)                       // focusable = true → chạm ra ngoài là tự đóng
        .apply { showAsDropDown(anchor) }  // neo ngay dưới dấu ••• vừa bấm
}

override fun onClick(v: View?) {
    popup?.dismiss()                       // đóng TRƯỚC rồi mới chạy hành động
    when (v?.id) {
        R.id.lblEdit -> onEdit?.invoke()
        R.id.lblDel  -> onDelete?.invoke()
    }
}
Vì sao dismiss() phải chạy trước: nếu gọi hành động trước, hộp thoại xác nhận xóa hiện lên trong khi popup vẫn còn, popup nằm đè lên và người dùng không bấm được nút "Có". Đảo thứ tự là hết.
Điểm còn tối ưu được: menuitem.xml có gốc là <LinearLayout> chứ chưa dùng <merge>, nên khi thổi vào MenuItemFrag (bản thân đã là LinearLayout) sẽ có một LinearLayout lồng trong LinearLayout. Chạy vẫn đúng, chỉ thừa một cấp. Nếu thầy hỏi "chỗ nào cải tiến được" thì đây là câu trả lời sẵn.

06Ngày sinh & DatePicker

Ô ngày sinh cố tình không cho gõ tay để khỏi phải kiểm tra chuỗi ngày sai định dạng.

XMLadd.xml — txtDob
<EditText
    android:id="@+id/txtDob"
    android:clickable="true"       ← vẫn nhận cú chạm
    android:focusable="false"      ← không nhận con trỏ, không bật bàn phím
    android:inputType="none"
    android:hint="dd/mm/yyyy"
    android:drawableEnd="@drawable/ic_dropdown" />
KotlinAddAct.kt — mở lịch
txtDob.setOnClickListener {
    val format = SimpleDateFormat("dd/MM/yyyy", Locale.getDefault())
    val calendar = Calendar.getInstance()
    val typed = txtDob.text.toString().trim()
    if (typed.isNotEmpty()) format.parse(typed)?.let { calendar.time = it }

    DatePickerDialog(this,
        { _, year, month, dayOfMonth ->
            val picked = Calendar.getInstance()
            picked.set(year, month, dayOfMonth, 0, 0, 0)
            picked.set(Calendar.MILLISECOND, 0)
            txtDob.setText(format.format(picked.time))
        },
        calendar.get(Calendar.YEAR),
        calendar.get(Calendar.MONTH),
        calendar.get(Calendar.DAY_OF_MONTH)).show()
}
  • Tháng đếm từ 0. Calendar.JANUARY == 0. Callback của DatePicker trả về month đã theo hệ 0 nên truyền thẳng vào picked.set(...) là đúng. Chỗ duy nhất phải trừ 1 là khi tự gõ tay dữ liệu mẫu: set(year, month - 1, day, …).
  • Xóa giờ phút giây. Calendar.getInstance() mang theo thời điểm hiện tại; không đặt lại về 0 thì hai ngày sinh "giống nhau" vẫn khác nhau ở phần mili giây.
  • Ngày chỉ sống dưới dạng chữ trong ô txtDob, đến lúc bấm Lưu mới parse ra Date. Nhờ vậy AddAct/EditAct không phải mang thêm biến nào ngoài UML.
  • Locale.getDefault() — dùng cùng một locale cho cả format lẫn parse, tránh cảnh máy đặt tiếng khác thì đọc lại không ra.

07ListView & Adapter

KotlinUserhomeAct.kt — adapter
adapter = object : ArrayAdapter<User>(this, 0, listUser) {
    override fun getView(position: Int, convertView: View?, parent: ViewGroup): View {
        val row = convertView as? ShowUserFrag ?: ShowUserFrag(this@UserhomeAct)
        row.bind(listUser[position])
        row.setOnMenuClickListener { anchor -> /* mở menu cho dòng này */ }
        return row
    }
}
lwUsers.adapter = adapter
  • Tham số 0 ở chỗ layout id: vì getView đã bị ghi đè hoàn toàn nên adapter không cần layout mặc định nào cả.
  • convertView là View cũ được tái sử dụng. ListView chỉ giữ đủ số dòng nhìn thấy; cuộn xuống thì dòng vừa trôi khỏi màn hình được giao lại cho dòng mới. Hệ quả: mọi thứ phụ thuộc position phải gán lại mỗi lần — cả nội dung (bind) lẫn listener. Gán một lần lúc tạo là sai, vì dòng đó sau này mang dữ liệu người khác.
  • notifyDataSetChanged() báo cho ListView rằng nguồn dữ liệu đã đổi để nó vẽ lại. Sửa listUser mà quên gọi thì màn hình vẫn hiện dữ liệu cũ.
  • listUser phải được sửa tại chỗ (add, removeAt, gán theo chỉ số). Gán một danh sách mới cho biến khác thì adapter vẫn trỏ vào danh sách cũ.

11Sự cố thực tế đã gặp

1. Nửa trên màn Home biến mất

Hiện tượng: lời chào, tiêu đề và nút "Thêm mới" không thấy đâu, chỉ còn danh sách.

Chẩn đoán: đọc XML mãi không ra. Đổ cây view thật bằng adb shell uiautomator dump thì thấy action_bar_container chiếm [0,0][1344,327] đè lên nội dung cũng bắt đầu từ [0,0].

Nguyên nhân: Android 15 với targetSdk 35 ép chế độ tràn viền (edge-to-edge).

Cách sửa: theme riêng, không ActionBar và tắt ép tràn viền:

XMLvalues/themes.xml
<style name="Theme.LoginApp"
       parent="@android:style/Theme.DeviceDefault.Light.NoActionBar">
    <item name="android:windowOptOutEdgeToEdgeEnforcement">true</item>
</style>
Bài học rút ra: khi giao diện "biến mất" mà XML trông đúng, hãy đổ cây view thật đang chạy thay vì đọc lại file.

2. attribute layout_constraint… not found

ConstraintLayout là thư viện ngoài, script build thủ công không tự biết. Cách sửa: giải nén file .aar vào vendor/, đưa res của nó vào bước compile/link và đưa jar vào kotlinc + d8.

3. Tách bài ra thì layout đè nhau

Bài 3 và bài 4 cùng có login.xml, userhome.xml… nội dung khác nhau. Một thư mục res chung thì file này đè file kia. Cách sửa: mỗi bài một thư mục res-baiXX và một manifest riêng, script chọn theo tham số.

4. Bốn ô nhập lệch nhau vài pixel

Nhãn để wrap_content nên "Username:" dài hơn "DoB:", kéo theo điểm bắt đầu của ô nhập lệch. Cách sửa: cho cả 4 nhãn bề rộng cố định 140dp.

12Bộ câu hỏi & trả lời

Bấm vào câu hỏi để mở đáp án. Nhóm A–D là phần chắc chắn bị hỏi.

A · Vòng đời và điều hướng

A1Vì sao sau khi đăng nhập lại gọi finish()?▶

finish() gỡ LoginAct khỏi ngăn xếp. Nếu không gỡ, người dùng ở màn Home bấm Back sẽ quay lại màn đăng nhập — mà lúc đó họ đã đăng nhập rồi, quay lại là vô nghĩa và còn cho phép đăng nhập chồng lên. Bỏ finish() thì Back phải bấm hai lần mới thoát.

A2onCreate, onResume, onActivityResult chạy theo thứ tự nào khi quay về từ màn Thêm?▶

onActivityResult chạy trước onResume. Cụ thể: màn Thêm gọi finish() → hệ thống gọi onActivityResult của màn Home → rồi mới onRestart → onStart → onResume.

Hệ quả thực tế: dữ liệu đã được ghi vào listUser xong xuôi trước khi màn hình hiện lại, nên không bao giờ thấy cảnh nhấp nháy dữ liệu cũ. onResume trong bài này gọi thêm notifyDataSetChanged() chỉ là lớp bảo hiểm.

A3Xoay màn hình thì danh sách có mất không?▶

Có. Xoay làm Activity bị hủy và tạo lại, listUser nằm trong bộ nhớ của Activity nên mất sạch, onCreate chạy lại và nạp lại 4 người mẫu. Muốn giữ thì phải lưu vào onSaveInstanceState, hoặc ViewModel, hoặc chờ bài 5 dùng SQLite. Đây là điểm yếu cố ý của bài "chưa có CSDL".

A4Vì sao dùng Activity chứ không phải AppCompatActivity?▶

Đúng theo slide: dùng View system cổ điển, không kéo thêm thư viện AndroidX ngoài ConstraintLayout. AppCompatActivity đi kèm cả gói appcompat và bắt buộc theme Theme.AppCompat. Đổi lại, ở đây không có supportActionBar, không có tương thích ngược của theme — chấp nhận được vì minSdk 24.

B · Truyền dữ liệu

B1Serializable và Parcelable khác nhau ra sao? Vì sao chọn Serializable?▶

Serializable là cơ chế của Java, dùng phản chiếu (reflection) nên chậm hơn và sinh rác nhiều hơn, bù lại chỉ cần thêm một chữ vào khai báo lớp. Parcelable là của Android, tự viết cách đọc/ghi nên nhanh hơn đáng kể.

Bài này mỗi lần chỉ truyền một đối tượng nhỏ, chênh lệch không đáng kể, và slide cũng vẽ như vậy. Nếu bị hỏi "khi nào phải đổi": khi truyền danh sách lớn hoặc truyền liên tục.

B2requestCode để làm gì? Bỏ đi được không?▶

Một Activity có thể mở nhiều màn con khác nhau, nhưng tất cả kết quả đều rơi vào cùng một hàm onActivityResult. requestCode là nhãn ta tự đặt lúc đi, hệ thống trả nguyên lại lúc về, nhờ đó phân biệt được "cái vừa về là của Thêm hay của Sửa". Bỏ đi thì thêm mới và sửa sẽ lẫn lộn.

B3resultCode là gì, vì sao phải kiểm tra?▶

Là kết quả có thành công hay không. Bấm "Thêm" thì màn con gọi setResult(RESULT_OK, intent); bấm "Hủy" hoặc bấm Back thì kết quả mặc định là RESULT_CANCELED và không kèm dữ liệu. Không kiểm tra thì lúc người dùng bấm Hủy, data là null và app sẽ văng.

B4startActivityForResult bị đánh dấu lỗi thời, sao vẫn dùng?▶

Bản thay thế là registerForActivityResult với Activity Result API, nhưng nó nằm trong thư viện AndroidX Activity — thêm phụ thuộc mà bài này cố tình không dùng. Hàm cũ vẫn chạy đúng trên mọi bản Android hiện có. Slide cũng dạy theo cách cũ. Biết cả hai và giải thích được lý do chọn là đủ.

B5Vì sao đọc getSerializableExtra phải chia hai nhánh?▶

Từ API 33 (Tiramisu), Android thêm bản có tham số kiểu — getSerializableExtra("user", User::class.java) — để kiểm tra kiểu ngay lúc đọc, an toàn hơn; bản một tham số bị đánh dấu lỗi thời. Nhưng minSdk của app là 24, máy cũ không có hàm mới. Nên phải hỏi Build.VERSION.SDK_INT rồi chọn nhánh.

C · ListView và Adapter

C1convertView là gì? Không dùng có sao không?▶

Là một dòng cũ đã trôi khỏi màn hình, ListView đưa lại để dùng tiếp thay vì tạo View mới. Không dùng (luôn ShowUserFrag(context) mới) thì danh sách dài sẽ giật và tốn bộ nhớ, vì mỗi lần cuộn lại thổi layout lại từ đầu.

C2Vì sao setOnMenuClickListener phải gọi lại mỗi lần getView chạy?▶

Vì listener bắt giữ biến position. Dòng số 0 sau khi cuộn có thể được tái sử dụng cho dòng số 7 — nếu listener cũ còn nguyên, bấm ••• ở dòng 7 sẽ đi sửa dòng 0.

Nói ngắn gọn: convertView mang theo trạng thái cũ, nên mọi thứ phụ thuộc vị trí đều phải gán lại — cả nội dung lẫn sự kiện.

C3notifyDataSetChanged() làm gì? Vì sao xóa xong phải gọi?▶

Nó báo cho ListView rằng nguồn dữ liệu đã thay đổi, ListView sẽ hỏi lại adapter số dòng và vẽ lại. Xóa khỏi listUser mà không gọi thì danh sách trên màn hình vẫn còn dòng cũ — thậm chí bấm vào dòng đó sẽ gây lỗi vượt chỉ số.

C4Vì sao truyền 0 vào chỗ layout của ArrayAdapter?▶

ArrayAdapter bình thường dùng layout đó để tự vẽ mỗi dòng bằng một TextView. Ở đây getView đã bị ghi đè hoàn toàn, dòng do ShowUserFrag tự dựng, nên tham số ấy không được dùng đến. Truyền 0 là quy ước cho "không cần".

C5ListView và RecyclerView khác nhau thế nào?▶

RecyclerView mới hơn, bắt buộc dùng ViewHolder (ListView chỉ khuyến khích), tách riêng phần bố cục qua LayoutManager, có hoạt ảnh thêm/xóa sẵn, và cập nhật từng dòng thay vì vẽ lại cả danh sách. Đổi lại nó nằm trong AndroidX và viết dài hơn. Bài học dùng ListView cho đúng phạm vi slide.

D · Custom View và menu

D1ShowUserFrag có phải Fragment không?▶

Không. Tên có chữ "Frag" theo slide, nhưng nó kế thừa ConstraintLayout, tức là một View. Fragment thật có vòng đời riêng, cần FragmentManager để gắn vào Activity. Ở đây chỉ cần một khối giao diện tái sử dụng nên custom View là đúng và nhẹ hơn.

D2<merge> dùng để làm gì?▶

Khi thổi một layout vào bên trong một ViewGroup đã có sẵn, nếu layout đó có gốc là ConstraintLayout nữa thì kết quả là ConstraintLayout lồng ConstraintLayout — thừa một cấp, vẽ chậm hơn. <merge> nói "đừng tạo gốc, đổ thẳng các con vào cha".

tools:parentTag đi kèm chỉ phục vụ khung xem trước trong Android Studio, để nó biết coi các con này nằm trong loại ViewGroup nào mà vẽ. Không ảnh hưởng lúc chạy.

D3@JvmOverloads ở constructor để làm gì?▶

Hệ thống thổi layout gọi constructor (Context, AttributeSet) bằng phản chiếu khi gặp thẻ custom View trong XML. Kotlin viết tham số mặc định thì chỉ sinh ra một constructor đủ tham số. @JvmOverloads bảo trình biên dịch sinh thêm các bản rút gọn, nhờ đó View đặt được trong XML.

D4Vì sao PopupWindow đặt focusable = true?▶

Để popup nhận sự kiện chạm ngoài vùng của nó và tự đóng. Đặt false thì bấm ra ngoài popup vẫn dính trên màn hình, phải bấm đúng một mục mới đóng — trải nghiệm sai.

D5showAsDropDown khác showAtLocation chỗ nào?▶

showAsDropDown(anchor) neo popup ngay dưới một View mốc, tự tính tọa độ — đúng nhu cầu "xổ ra ngay dưới dấu ••• của dòng đó". showAtLocation đặt theo tọa độ tuyệt đối trong cửa sổ, phải tự tính, thường dùng cho popup giữa màn hình.

D6Vì sao dismiss() gọi trước khi chạy hành động?▶

Vì hành động "Xóa" mở một AlertDialog xác nhận. Nếu popup còn đó, nó nằm trên hộp thoại và che mất nút "Có". Đóng trước rồi mới gọi callback là hết. Đây là lỗi đã thực sự gặp khi làm bài, không phải giả định.

D7Vì sao MenuItemFrag nhận hai hàm lambda thay vì tự làm việc?▶

Để nó chỉ lo phần giao diện — hiện menu, bắt cú bấm — còn việc sửa hay xóa ai thì là chuyện của màn Home vì chỉ Home mới giữ listUser. Nhờ vậy cùng một lớp menu dùng lại cho mọi dòng, chỉ cần truyền vào việc cần làm khác nhau.

E · Layout và tài nguyên

E1layout_width="0dp" trong ConstraintLayout nghĩa là gì?▶

Nghĩa là "giãn theo ràng buộc" (match constraints) — chiều rộng được quyết định bởi mốc trái và mốc phải, chứ không phải bởi nội dung. Đây là cách để một ô nhập kéo dài từ sau nhãn tới mép phải. Dùng match_parent trong ConstraintLayout là sai quy ước và có thể cho kết quả bất ngờ.

E2layout_constraintBaseline_toBaselineOf khác gì với căn theo Top?▶

Nó căn theo đường chân chữ, nên nhãn "Username:" và chữ trong ô nhập nằm cùng một đường ngang dù hai view cao thấp khác nhau (ô nhập có padding và viền). Căn theo Top thì chữ trong ô nhập sẽ tụt xuống so với nhãn.

E3dp và sp khác nhau ra sao?▶

dp là đơn vị độc lập mật độ điểm ảnh — 1dp bằng 1 pixel trên màn 160dpi, hệ thống tự nhân lên ở màn dày hơn, giữ cho kích thước vật lý không đổi. sp giống dp nhưng còn nhân thêm hệ số cỡ chữ người dùng chọn trong Cài đặt. Vì thế: kích thước dùng dp, cỡ chữ dùng sp.

E4Lớp R là gì, ai sinh ra?▶

aapt2 sinh ra khi liên kết tài nguyên. Nó là một lớp Java chứa toàn hằng số nguyên, mỗi tài nguyên một số: R.layout.add, R.id.txtUN, R.drawable.bg_menu. Nhờ đó mã nguồn tham chiếu tài nguyên bằng số chứ không bằng chuỗi, sai tên là báo lỗi ngay lúc biên dịch.

E5Vì sao tên file trong res/ phải viết thường?▶

Vì tên file trở thành tên trường trong lớp R, và aapt2 chỉ chấp nhận chữ thường, chữ số và gạch dưới. Đó là lý do UML ghi ShowUser.xml nhưng file thật phải là showuser.xml.

E6drawable dạng XML là gì? Sao không dùng ảnh?▶

<shape> mô tả hình bằng chữ: nền, viền, độ bo. Hệ thống vẽ ra lúc chạy nên sắc nét ở mọi độ phân giải và nhẹ hơn ảnh nhiều. ic_dropdown.xml là <vector> — cũng vẽ bằng đường, cùng ưu điểm.

F · Ngày tháng

F1Vì sao trong dữ liệu mẫu lại viết month - 1?▶

Vì Calendar đếm tháng từ 0: tháng 1 là 0, tháng 12 là 11. Hàm phụ dateOf(2005, 3, 12) nhận tháng theo cách người đọc hiểu nên bên trong phải trừ 1. Ngược lại, month mà DatePickerDialog trả về đã theo hệ 0 rồi nên truyền thẳng, không trừ.

F2Vì sao ô ngày sinh để focusable="false"?▶

Để bấm vào ô là mở lịch chứ không bật bàn phím. Nếu để mặc định, ô nhận con trỏ, bàn phím hiện lên đè lên hộp lịch và người dùng gõ được chuỗi lung tung — lại phải viết thêm phần kiểm tra định dạng. Chặn ở giao diện rẻ hơn kiểm tra ở mã.

F3Date đang lưu cả giờ phút giây, có sao không?▶

Có, nếu không đặt lại. Nên trong cả dateOf lẫn callback của DatePicker đều gọi set(…, 0, 0, 0) và set(Calendar.MILLISECOND, 0). Không làm thì hai ngày sinh cùng ngày vẫn khác nhau khi so sánh, và hiển thị thì không thấy khác biệt nên rất khó tìm ra lỗi.

F4Vì sao User.dob là Date chứ không phải Date??▶

Để khớp UML (slide ghi dob : Date) và vì màn Thêm đã bắt buộc chọn ngày trước khi cho lưu, nên không có trạng thái "chưa có ngày sinh" lọt vào danh sách. Việc kiểm tra rỗng làm ở tầng giao diện — ô txtDob còn trống thì không cho bấm Thêm.

G · Kiểm tra dữ liệu & thiết kế

G1Chặn trùng username làm ở đâu, vì sao đặt ở đó?▶

Làm trong UserhomeAct.onActivityResult. Lý do: chỉ màn Home mới giữ listUser, nên đặt ở đó thì hai màn con không phải mang thêm biến nào ngoài sơ đồ lớp.

Đánh đổi phải nói rõ nếu bị hỏi: kiểm tra sau khi màn con đã đóng nên dữ liệu vừa gõ bị mất, người dùng phải nhập lại. Muốn giữ lại thì phải truyền danh sách username sang màn con và kiểm tra tại chỗ — đổi lại là thêm một biến không có trong UML.

G2Khi sửa, đổi username thành tên của chính mình có bị chặn không?▶

Không. Phép kiểm tra bỏ qua chính dòng đang sửa: i != editingPosition. Nếu không bỏ qua thì bấm Lưu mà không đổi gì cũng bị báo trùng.

G3Vì sao so sánh username bằng ignoreCase = true?▶

Để ND1 và nd1 bị coi là một. Tên đăng nhập phân biệt hoa thường rất dễ gây nhầm khi đăng nhập, nên chuẩn chung là không phân biệt.

G4Mật khẩu đang để nguyên văn trong bộ nhớ — có vấn đề gì không?▶

Có, và cần nói thẳng là bài tập cố tình đơn giản hóa. Ứng dụng thật phải băm mật khẩu (bcrypt/Argon2) và không bao giờ lưu nguyên văn, cũng không truyền qua Intent. Ở đây dữ liệu chỉ sống trong RAM, không ghi ra đâu cả, và tài khoản đăng nhập cũng là hardcode — phạm vi bài học là luồng màn hình, không phải bảo mật.

G5Vì sao bỏ component UserFormView đã làm ở bài trước?▶

Vì UML slide 7 vẽ 4 ô nhập nằm thẳng trong add.xml/edit.xml và trong AddAct/EditAct. Component là thiết kế tốt hơn về mặt tránh lặp, nhưng yêu cầu là khớp sơ đồ. Nếu được hỏi "cách nào hay hơn": component — vì phần thân hai màn giống hệt nhau, gom lại thì sửa một chỗ ăn cả hai.

H · Công cụ và build

H1Vì sao không dùng Gradle?▶

Để thấy rõ từng bước: biên dịch tài nguyên, sinh R, biên dịch mã, chuyển DEX, đóng gói, ký, cài. Gradle làm hết những việc đó nhưng giấu đi. Ngoài ra một module Gradle chỉ nhận một namespace, mà ở đây muốn dựng hai app từ cùng một thư mục. Cấu hình Gradle vẫn còn, đang trỏ vào bài 4.

H2Vì sao APK phải ký mới cài được?▶

Android dùng chữ ký để xác định "cùng một tác giả" — bản cập nhật phải ký cùng khóa với bản đã cài, nếu không hệ thống từ chối. APK không ký thì không cài được kể cả trên máy ảo. Ở đây dùng khóa debug có sẵn (~/.android/debug.keystore), chỉ hợp cho phát triển.

H3Hai app cài song song bằng cách nào?▶

Android phân biệt ứng dụng bằng applicationId ghi trong manifest. Bài 3 là ...bai03, bài 4 là ...bai04, khác nhau nên hệ thống coi là hai app, mỗi cái một biểu tượng và một vùng dữ liệu riêng. Tên hiện dưới biểu tượng là android:label.

H4Làm sao biết một View đang thực sự nằm ở đâu trên màn hình?▶

adb shell uiautomator dump rồi kéo file XML về đọc. File đó liệt kê mọi View đang hiển thị kèm resource-id, text và bounds theo pixel thật. Đây là cách tìm ra lỗi tràn viền ở mục 11 — nhìn XML nguồn thì không bao giờ thấy.

I · Câu hỏi mở

I1Ứng dụng này còn thiếu gì so với app thật?▶
  • Dữ liệu mất khi xoay màn hình hoặc thoát app — bài 5 sẽ thêm SQLite.
  • Mật khẩu lưu nguyên văn.
  • Không kiểm tra định dạng: username có thể chứa khoảng trắng, mật khẩu không giới hạn độ dài.
  • Không có tìm kiếm, không phân trang.
  • Chuỗi hiển thị viết thẳng trong code thay vì đưa vào strings.xml — làm đa ngôn ngữ sẽ phải sửa lại.
I2Nếu danh sách có 10.000 người thì chỗ nào chết trước?▶

Phép chặn trùng username đang duyệt tuyến tính cả danh sách mỗi lần thêm — chậm dần. Sửa bằng một HashSet tên đã dùng. Còn ListView thì vẫn ổn nhờ tái sử dụng View, vì nó chỉ dựng đúng số dòng nhìn thấy.

I3Vì sao dùng ConstraintLayout mà không phải LinearLayout?▶

ConstraintLayout dựng được bố cục phẳng — không phải lồng nhiều lớp ViewGroup để căn chỉnh, nên đo đạc nhanh hơn. Nó cũng cho căn theo đường chân chữ, thứ mà LinearLayout không có, và đó chính là cách nhãn với ô nhập nằm thẳng hàng ở đây.
